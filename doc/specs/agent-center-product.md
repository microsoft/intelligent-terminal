# Agent Center：以工作为中心使用操作系统

**产品规格 v0.7 · Work 与独立执行会话：从意图到可验收结果**

本文定义产品的完整目标体验。界面、操作、数据与结果均为设计示例，
实现状态由交付进度单独记录。领域规则见 [agent-center.md](agent-center.md)。
具体实现遵循 [协作协议 v1](agent-center-protocol.md)：消息、回包、
驱动责任、执行续接和验收返工都有确定契约，而不是交给各模块自行解释。

产品目标是让 Terminal 成为在操作系统中完成工作的最简单入口。
当前以真实开发工作作为第一个验证场景：系统能否接住任务组织、内部信息交接、
检查与返工，让用户围绕目标、重要判断和可用结果开展工作。
开发、验收等 Agent 分工是实现手段，不是产品范围；本地代码和报告交付通过，
不代表任意操作系统任务、应用自动化或已有进程接管已经可用。
原型采用真实任务、执行与产物；生产级可用性、安全性和恢复能力另行验证，
不作为这轮体验实验的前置门槛，也不因一次演示就被宣称已经具备。

## 1. 产品要解决的根本问题

> **Terminal is the easiest way to get tasks done on your OS.**

用户通过一个 Terminal 表达目标、使用获准的操作系统资源并获得可验收结果。
工作可能是修复代码、准备运行环境、诊断应用或整理文件；用户讨论的是
“做什么、在哪里做、进度如何、为什么这样做、换个方案、我来验收”，
而不是“打开哪个 shell、启动哪个 Agent、压缩哪个会话的上下文”。

这不是从 command-driven 改成 agent-driven，而是 **task-driven**：
工作是用户组织活动的基本单位，命令、Agent、shell、会话和模型是执行资源。
“只需要一个 Terminal”指完成受支持工作的统一人机入口，不是重写操作系统、
替代所有应用，或不经授权接管机器上的全部进程。

一项工作可能包含调查、操作、验证、取舍、协作与交付。
多项工作同时进行时，人的注意力成为最稀缺的资源。
产品应当承担可以被委托的推进过程，把人的注意力留给目标、重要取舍和最终结果。

**整个 Terminal 是运行环境；每个窗口的 Agent Console 是唯一工作入口。**
用户在这个入口表达目标、授权推进、切换工作、做决定和接受交付。
Agent Console 使用 keyboard-first TUI；工作能力由可独立运行的后台服务提供。
本文把这个窗口级 Agent Pane 称为 Agent Console。

用户始终能回答四个问题：

| 问题 | 产品提供的答案 |
|---|---|
| 我在推进什么？ | 稳定的工作目标、执行位置、优先级和完成条件 |
| 事情进展到哪里了？ | 有依据的阶段、已形成的结果、接下来将发生的动作 |
| 现在需要我做什么？ | 带上下文、选项和影响说明的决定、验收或修复 |
| 我得到了什么？ | 可检查、可复用、可追溯到约定目标的产物或状态变化 |

“为什么采用这个方案”必须依据实际计划、约束、决定和证据回答；
“换个方案”必须形成可确认的影响和真实执行变化，不能只有聊天承诺。

### 1.1 责任分工

| 用户负责 | 产品负责 |
|---|---|
| 表达想得到的结果 | 把输入整理成工作约定与可执行计划 |
| 确认范围、质量和授权边界 | 在边界内选择能力与执行位置、安排执行、传递上下文 |
| 做影响产品、风险和资源投入的取舍 | 组织问题与证据，给出建议和明确后果 |
| 检查并接受最终交付 | 汇总结果、验证依据、未解决事项及交付动作 |
| 随时调整方向或接管 | 安全交接、保存现场、重新安排受影响的工作 |

产品的成功标准是：**人做出的每一次判断都改变了工作方向、授权或结果，
而日常推进能够连续发生。**

### 1.2 六个体验原则

1. **从意图开始。** 用户先说想完成什么，系统组织其余信息。
2. **授权一次，持续推进。** 在确认的范围和预算内，阶段交接、验证与适当的重试自动进行。
3. **重要判断集中出现。** 每条待办都带着具体问题、所需背景、影响和可执行动作。
4. **现场随时可进入。** 计划、对话、代码、终端、证据属于同一项工作。
5. **结果能够被检验。** 交付明确对应完成条件，结论有来源和版本。
6. **控制权始终清楚。** 用户知道系统正在做什么、还被允许做什么，以及怎样介入。

### 1.3 当前验证范围与后续能力

| 阶段 | 要证明的用户价值 | 边界与进度口径 |
|---|---|---|
| 当前工作模式实验 | 在一个入口对话、委托并行工作、理解和调整方案、内部返工、人工贡献与验收 | 使用已配置且获准的本地开发环境；v1 交付为 `LocalCode` / `Report`。第 11 节 J1–J9 必须逐项有证据，不能只用组件通过数签收 |
| 后续资源连续性验证 | 已有受管现场或执行者更换后，仍是同一件工作，不要求用户整理会话和重述上下文 | 逐适配器验证注册、授权、输入交接、停止与恢复；不能声称任意 Agent、shell 或进程均可调度 |
| 后续 OS 结果验证 | 环境准备、应用诊断、文件处理等工作直接改变并验证目标状态 | 先定义状态目标、适配器权限、观测与恢复契约，再扩展协议和实现；报告文件不能冒充实际状态改变 |

功能、命令和 Agent 数量不用于替代这三个阶段的结果证据。基础输入可靠性
是完成工作所必需的条件，但只修好输入或增加 shell 管理命令不构成产品闭环。
当前试点的安全边界必须成立；“后续资格验证”不是越权执行或忽略未知副作用的许可。

#### 当前实现顺序

当前优先交付的故事是：**我交办 A，再交办 B；随时了解进展、处理必要决定、
检查并验收结果，不需要复制内部标识或管理内部执行者。**

| 增量 | 交付条件 |
|---|---|
| 可操作的双工作主流程 | 已配置项目中，从自然语言委托进入可读约定与明确确认；按目标选择工作，查看真实进展、回答问题、检查和验收固定交付。后台流量与重连不破坏选择、草稿和待确认动作 |
| 完整工作协作者 | 接通授权范围内的全局事实问答、方案依据和确认后的真实方案替换；普通讨论不改变执行，对应完整 J9 |
| 连续自主闭环 | 在同一明确构建上完成 J1–J9，包括真实必需检查失败后的内部返工、两项明确验收的实际交付和零必要人工内部编排 |

这个顺序划分实现增量，不降低当前试点的最终签收门槛。第一项不能替代完整
J9，也不能把表单或脚本驱动的操作记成真实模型自主完成。资源连续性与 OS
状态结果仍属于后续资格验证，不通过增加管理命令或页面提前宣称支持。

## 2. 产品形态

### Work 与执行者的归属

**Master 不直接执行；每个 Work 拥有一个固定的执行 Agent session。**
这是工作归属和消息路由的约束，不是把原来的工作协调器改一个名字。

```text
Master / 全局聊天
  ├── Work A ── Executor Session A
  ├── Work B ── Executor Session B
  └── Work C ── Executor Session C
```

Master 理解新目标、创建和分派 Work、汇总跨工作状态，并提出需要确认的管理操作。
文件修改、命令执行、项目启动和验证由相应 Work 的执行者完成。
打开 Work 后，输入直接进入这个执行会话，不再先唤醒一个仅负责登记、规划、
派发临时执行者的工作协调器。内部步骤和工具调用不是用户必须管理的另一层工作。

同一 Work 的聊天、继续、恢复和“在标签页打开”共享同一个执行会话与输入队列。
执行者忙碌时，消息按顺序等待处理并明确展示排队状态；切换视图不切换执行身份，
也不创建第二个写入者。会话恢复必须证明原会话已加载；不能恢复时说明原因，
不得静默新建会话并宣称恢复成功。

一次聊天回复结束不等于 Work 完成，也不应自动杀死为该 Work 启动的开发服务器。
执行者可以进入空闲状态，保留上下文与获准的运行资源，等待用户继续交互或验证。
暂停、取消、服务关闭及恢复交接分别执行对应的受管停止和释放流程，
授权范围、执行预算和独占写入约束仍然有效。

历史 Task/Attempt、验证和返工记录保持可读、可追溯。迁移旧 Work 时必须先停止
旧调度、完成写入者交接，再绑定经过验证的执行会话，不能把协调会话冒充执行会话。
旧执行模型的兼容性不应迫使新 Work 继续经过同一套协调器与临时任务链。

**当前实现边界：** 本轮先打通执行、续聊和恢复；新 Work 的正式交付验收后续补齐，
当前明确返回不支持，不把普通回复算作已完成或已验收。旧模式的交付验收不变。
每个实际获准执行的输入回合占用一次执行额度并受执行时限约束；排队本身不计次，
附着到仍存活的同一会话也不计次。空闲执行者仍持有工作区和并发名额，
需要释放这些资源时应明确暂停或取消，而不是把关闭聊天视图当作结束执行。

### 2.1 窗口里只有一个 Agent Console

Agent Console 属于窗口，而工作、Agent 执行和 shell 各有独立身份。
它可以管理多项工作，并切换正在查看的上下文。
一项工作可以使用零个、一个或多个 shell 与执行现场；物理 Tab 用来呈现运行资源。

窗口的结构是：

```text
Terminal Window
└── Window-level layout
    ├── AgentConsoleHost                 独立 XAML 宿主
    │   └── Agent Console TUI             本窗口唯一工作入口
    │       ├── 全局工作与待办
    │       ├── 当前工作对话与交付
    │       └── 统一输入区 / slash commands
    └── ShellWorkspaceHost               按需显示
        ├── Shell / Terminal Tab A
        ├── Shell / Terminal Tab B
        └── 执行输出与其他现场视图
```

Agent Console 与 shell 区域是窗口布局中的兄弟节点。
XAML 负责宿主、布局、焦点与窗口集成；TUI 负责工作界面、聊天、
streaming、问题卡和命令交互。
一个窗口中的多个工作和执行共享这个入口，各自保留独立的状态与授权。

### 2.2 默认直接进入任务列表

打开窗口后，Agent Console 占据主要内容区域，shell 区域隐藏。
默认显示简洁任务列表，顶部持续显示“F1 全局聊天 / F2 任务”导航；
已有任务显示真实状态和最近活动。
打开任务进入该 Work 执行者的对话，不自动展开计划、协议或执行详情。
启动这个入口直接启动 TUI 客户端，用户的 PowerShell、cmd 或其他 shell
只在需要交互现场时创建。

TUI 自身的终端渲染通道和承载进程属于界面基础设施。
用户 shell、工作执行会话与物理 Tab 按各自用途创建，
打开工作入口不要求存在一个默认 shell Tab。

用户可以始终停留在 Agent Console 中完成创建、推进、决定和验收。
后台任务通过执行服务运行，是否展示 shell 是独立的呈现选择。
Agent Console 是沿用的界面名称，不要求用户先理解 Agent、Provider 或会话。
在已批准的环境策略内，shell 类型、执行能力和上下文传递由系统安排；
首次权限、数据目的地或费用选择仍须向用户明确披露，不能以“简单”为由隐藏。

**Intelligent Terminal is the shell; natural language is the command.**
新建任务与跨任务查询使用全局对话；打开已有任务则进入该任务的独立对话，
明确显示状态、最近活动与继续入口。项目与工作是执行边界，不是普通问候或
问题的前置步骤，也不应为了接收一句话而创建空项目。每项任务与全局对话
分别保留草稿和阅读位置，切换时恢复对应状态。目标、位置或必要信息不明确时，
用自然语言澄清，而不是要求
用户学习 `/project use <id>`、复制 GUID 或填写协议 JSON。

slash command 保留为可选的精确触发入口。自然语言触发的有后果操作先生成
绑定目标、参数、版本和权限的可读提议，用户明确确认后才执行。对自然语言
回答的解释不等于权限批准、正式开工或最终验收；聊天不能绕过这些边界。

### 2.3 两种窗口布局

| 布局 | 用户看到什么 | 进入方式 |
|---|---|---|
| Agent Focus | Agent Console 使用可用内容区，shell 区域隐藏 | 启动默认；`/shell hide` |
| Agent + Shell | 同一个 Agent Console 与选定 shell 并列或上下排列 | `/shell show <shell-id>`；首次使用 `/shell open` |

布局变化保持同一个 Console 会话、工作选择、草稿与阅读位置。
`/shell hide` 只隐藏显示；执行和交互会话按各自状态继续存在。
`/shell close <shell-id>` 才发起关闭指定会话的操作，并展示其执行影响。

窗口级 `FocusAgentConsole` 动作把焦点带回统一输入区，
默认键为 `Ctrl+Shift+G`，可配置。它由宿主处理，在 shell 获得焦点时也可用。
Agent Console 在混合布局中仍是工作管理入口，shell 提供直接操作运行环境的能力。

### 2.4 一处入口，多种工作视图

| Console 内视图 | 用户用途 | 直接命令 |
|---|---|---|
| 首页 | 默认任务列表；筛选全部或需要关注的任务，或表达新目标 | `/home` |
| 工作列表 | 查看和查找所有可访问工作 | `/work list` |
| 当前工作 | 状态、独立对话、继续任务；计划与执行记录按需查看 | `/work use <id>` |
| 待办 | 处理决定、验收和修复 | `/inbox` |
| 项目与知识 | 选择资源、约束与批准的上下文 | `/project show`、`/context show` |
| 历史 | 检查已结束工作和交付 | `/history` |

“工作站”指 Console 中聚合某项工作信息的视图，
它可以在 shell 全部隐藏时完整使用。
切换工作恢复该工作的对话、草稿、阅读位置、展开内容和待处理问题。
全局对话独立保留；它不是所有历史任务继续执行时必须经过的中转。
切换发生在当前窗口的 Console 视图内，后台执行保持自己的生命周期。

多个窗口各有一个 Console，并访问同一权限范围内的工作服务。
它们可以查看同一项工作，也可以分别关注不同工作。
一个窗口的查看位置和输入草稿与其他窗口分开保存。

### 2.5 工作上下文与 shell 上下文明确区分

Console 明确标识当前任务对话或新目标的全局对话。shell 区域显示会话号、
所属工作和目录。选择 shell Tab 改变查看的现场；用户可用自然语言指明工作，
也可通过可选的 `/work use` 或任务列表打开对应任务的对话。
若正在查看的 shell 属于另一项工作，界面同时标明这两个上下文，
并提供切换到对应工作的动作。

发送消息、回答决定和接受交付都绑定提交时明确显示的工作与对象版本。
执行过程中切换 Tab 或工作视图，不会改变已经提交操作的目标。

### 2.6 用户面对一个负责组织工作的协作者

用户在 Console 中使用同一个协作入口，但消息接收者由当前对话明确决定：
全局聊天面向不执行的 Master，Work 聊天面向该工作的固定执行者。
调查、实现和检查是 Work 内部的执行安排，用户无需在临时执行者之间搬运上下文。
统一入口不等于把每条 Work 消息都发送给 Master 或另一个协调会话。

例如用户正在查看导出修复，输入：

> 顺便调查一下构建慢的问题，导出那个先别动接口。

系统分别展示“建立构建调查工作”和“为导出工作保留接口约束”的理解。
若后者改变已确认约定，展示具体变更并等待确认。新工作不会悄悄吸收
原工作上下文；不能确定指代时，就地澄清。用户可以纠正理解。
理解回执说明目标工作与生效情况；当前视图保持，用户可直接进入新工作。

即时问答、工作内讨论、新委托、补充材料和目标变更分别处理。
“收到了材料”与“已按新材料调整执行”是不同反馈；
系统不会把一句补充说明暗中塞给正在使用另一份输入的执行者。

在 A 推进时，用户可以继续问“这些工作到哪了”“A 为什么采用这个方案”，
或讨论尚未决定的替代方案。系统从可访问的工作快照、计划理由、实际事件
和证据给出有来源、有更新时间的回答；未知进度明确为未知，不能用推测填补。
普通问答不修改授权、不自动暂停工作。全局讨论不会被暗中注入某个 Work；
在 Work 对话中发送的消息则按顺序交给该工作的执行者，不打断正在运行的当前回合。

“不行，换一个方案”进入显式变更流程：确认指代，解释替代方案与影响，
区分仍可复用的结果、需要收束的执行、新的权限或预算，再由用户确认相应变化。
如果当前能力无法处理跨工作查询或方案调整，应保留请求并明确说明边界，
不能要求用户逐一联系内部 Agent 后仍把这次体验计为自主完成。

## 2A. Keyboard-first：自然语言主路径与确定性命令

### 2A.1 统一输入区

用户始终可以从输入区表达目标、提问或输入确定性命令。
普通工作管理不以学习 slash command、复制内部 UUID 或编写 JSON 为前提。
自然语言和明确确认动作构成主路径；slash command 是可发现、精确和可自动化的
等价控制面，不是对话能力未实现时的验收替代品。
输入 `/` 打开可搜索命令列表，输入 `/work` 展示子命令，
输入参数时补全工作号、会话号、决定、交付和路径。
每个命令展示用途、参数、作用对象以及是否需要确认。

`Up` / `Down` 选择补全项，`Tab` 补全，`Enter` 提交，
`Esc` 返回输入。多行正文使用 `Shift+Enter` 换行。
命令提示打开时，历史浏览与候选选择采用明确的当前焦点规则。

首个非空白字符为 `/` 的输入进入命令解析。
以 `//` 开头表示正文中的字面 `/`；代码块按正文处理。
未知命令或无效参数显示错误并保留输入。
自然语言提议的工作动作最终进入相同的参数、版本和授权检查。

默认对象来自提交瞬间捕获的 Console 上下文，命令预览显示该对象。
工作级命令支持 `--work <id>` 明确指定目标；全局和视图命令使用自己的作用域。
在全局视图中缺少必需对象时，显示选择器。

#### 信息层级与直接操作

领域对象不直接决定用户界面。默认展示任务列表，打开任务即可对话；用户询问时，以真实依据
回答“做什么、做到哪里、下一步由谁负责、结果在哪里”。必要问题、风险确认、
失败和未知结果及时呈现，不把原始协议响应或常驻工作面板当成聊天内容。

| 层级 | 内容 |
|---|---|
| 默认展示 | 任务列表；打开后是任务状态、独立对话与继续入口；当前需要回答的问题、明确确认、失败或未知结果 |
| 按需展开 | 详细进展与下一责任方、计划、方案依据、实际执行位置、命令、检查结果、代码差异和交付 |
| 诊断详情 | 系统 GUID、attempt、revision、grant、关联标识和原始协议记录 |

内部标识继续用于正确关联、并发控制和追溯，但正常委托、确认、选择、回答和
验收不要求用户识别或输入它们。同名工作显示可读的项目或目标背景并要求明确
选择，不能模糊匹配到另一项工作。用户正文、文件内容、真实路径或证据本身
包含标识时不得擅自改写；隐藏实现细节也不能隐藏风险、未知状态或失败原因。

选择器、问题表单和动作卡复用相同的领域操作。字段按照服务提供的响应 schema
收集并保留类型；不支持的 schema 明确说明，不退回让用户手写 JSON 后仍宣称
主路径可用。操作预览以可读目标、内容和影响解释精确的请求；确认仍绑定内部
参数、版本和命令身份。取消、冲突和重连不等于批准，不能自动重发有副作用的
操作。检查交付为只读，最终验收另行明确确认，不能把接受子任务作为人工职责。

后台更新不抢输入。连接中断时显示事实可能过期，保留各对话草稿与阅读位置；
恢复后重新取得有效状态，不能要求关闭 Console、重建工作或搬运上下文。

#### 工作界面的布局

工作界面保持 keyboard-first TUI，不另起一个与工作服务脱节的网页管理后台。
Agent Console 与现有 WTA Agent Pane 共用聊天消息、输入框、通用卡片和活动反馈的
呈现组件及主题；不建立另一套聊天视觉风格。两个入口各自适配消息与输入状态，
不混用后端会话、工作权限或审批状态。Console 只增加工作详情、确认与交付等领域界面。
布局按用户注意力组织，而不是给每种内部对象分配一个永久面板：

| 区域 | 默认内容与行为 |
|---|---|
| 工作导航 | 默认任务列表，显示简短目标、文字状态和最近活动；全部与需要关注是筛选，新建任务是独立入口 |
| 对话头部 | 标识实际选中的任务及真实执行状态；新建任务或跨任务问题才使用全局对话 |
| 工作主区 | 当前任务的持久对话，必要问题和确认在这里出现；不混入内部 worker 日志或默认展示协议面板 |
| 按需详情 | 工作范围、排除项、完成条件、实际执行位置和证据。展开不改变当前工作、输入草稿或授权 |
| 统一输入区 | 共用输入组件，但每项任务的草稿、选区和光标独立；打开其他任务或后台更新不能覆盖当前输入 |
| 确认层 | 显示冻结的目标、动作、内容与后果；风险、权限、数据去向和额度等必需信息不能以视觉简化为由藏掉 |

默认任务列表使用方向键选择、Enter 打开。只在统一的快捷键说明中标记一次
F4 动作菜单，不能在多个不同导航项前重复标记同一个快捷键。
打开任务后可返回任务列表；宽窗口可并列显示任务与对话，窄窗口使用单页切换。
工作详情按需打开，不是查看或继续旧任务的前置步骤。
详情空间不足时使用可返回的独立阅读层。
尺寸以终端字符显示宽度计算，中文、组合字符和宽字符不能按字节或代码单元裁切。
短窗口优先保留当前目标、可编辑输入与必要动作；不能只缩小正文而让固定装饰
占据大部分高度。所有可见动作都有确定的键盘入口，不能只有看似可点击的文字。

以留白、粗体、简洁分隔和少量语义色建立层次。状态必须有文字，不单靠颜色；
内部任务计数不能伪装成整体目标完成百分比。摘要来自服务事实，不为美观编造
阶段、时间、检查结果或建议。断线后明确称为“最后取得的事实”，不能继续声称
正在执行；操作结果未知与一般连接问题分别呈现，刷新不重发也不制造成功回执。

“继续任务”不是重新创建工作，也不是只发送一条全局聊天消息。仍在运行时连接
原执行，暂停时恢复已批准的工作；旧执行失联或超过截止时间时先核实、收束，
证明旧写入方已退出后才允许恢复。主协调会话可恢复时加载原会话，并重新绑定
当前工作授权与工具；无法恢复时明确说明，由用户另行选择按保存上下文新建会话，
不能把重新开始伪装成恢复成功。

“在 tab 中打开”呈现同一任务和服务管理的主会话，不启动第二个独立写入者，
也不绕过工作服务直接将旧工具凭据交给普通 helper。打开视图本身不授权执行。
内部 worker 可以有多个会话，但默认继续入口不要求用户理解或选择它们。

交付以可读名称、真实生成时间或确有依据的内容版本区分。“已检查的这份交付”
始终对应固定候选与内容；实体并发 `version` 不能直接解释为“报告第几版”。
项目源目录与受管执行目录分别标明，未知执行位置不得用源目录替代。

任务列表与独立任务对话是主入口，但界面与协议接通不等于真实模型业务旅程已经验收。
跨工作查询与提议需要各自的原生及模型证据；完整 J9 与后续 OS 能力仍按各自
交付条件推进，不能用 dashboard 或脚本适配器的通过代替。

### 2A.2 命令面覆盖

以下是目标命令契约。参数未完整填写时，TUI 提供相应选择器或表单；
动作卡与命令调用同一个操作。

| 目的 | 命令 |

| 导航与帮助 | `/home`、`/help [command]`、`/history` |

| 决定 | `/decision list`、`/decision show <id>`、`/decision answer <id>` |
| 待办 | `/inbox`、`/inbox seen <id>`、`/inbox snooze <id>` |
| 交付与验收 | `/review list`、`/review show <candidate-id>`、`/review accept <candidate-id>`、`/review revise <candidate-id>` |

明确内容和影响；需要确认的动作在确认后执行。
slash command 是完整的控制入口，不代表绕过工作权限和执行安全边界。
`/task` 和 `/result` 展示内部派发、结果与检查依据；`/review` 面向最终交付。
用户不需要通过逐个接受子任务来维持系统推进。

`delivery.accept`、`delivery.request_changes`；内部 `review.submit`
是检查者提交子任务评审，不是替用户接受最终交付。

### 2A.3 一个连续的键盘命令等价流程

```text
/work new "修复订单 CSV 导出漏行，保持列格式"
/work start
/work list
/work use W-7A2F
/plan show
/task list
/result show R-7
/decision answer D-102
/review show C-2
/review accept C-2
```

上述命令序列证明确定性控制覆盖，不单独证明自然语言工作模式。
创建、开始、回答和验收在相应位置展示必要预览或输入。
ID 以系统返回结果为准。仅检查产物时可直接使用 `/artifact` 命令。
需要亲自修改时，`/workspace takeover` 对应“我来改”，
`/workspace handback` 对应“改好了，交回工作”；每个动作组织完整的交接步骤。
shell 的显示和关闭分别控制，完整工作流程可以只使用键盘。

### 2A.4 相同能力面向人和 Agent

在普通终端中，`wta ui` 启动同一套 TUI 客户端；
在 Windows 窗口中，由 XAML 宿主直接启动并承载它。
无需图形窗口的调用者通过 `wta work ...` 等结构化 CLI 或 MCP 调用工作能力。
这些入口均属于本规格拟定义的能力。

例如：

```text
wta work list --json
wta work show W-7A2F --json
wta work events W-7A2F --after <cursor> --jsonl
```

工作操作共享同一套命令定义与权限。切换 Console 视图、隐藏 shell 等呈现动作
要求明确的视图/宿主目标；纯后台调用可以直接取得资源、结果和操作状态。
Agent 使用结构化工作状态和事件，不依赖模拟按键或读取 TUI 画面。

普通 TTY 中的 shell 交互由宿主适配器接管；前台子 shell 正常退出后返回 TUI。
非交互环境使用结构化输出、操作 ID 和事件游标。
需要人做决定时，返回明确的待输入状态并保存问题。

## 4. 从一句话形成工作约定

### 4.1 表达目标

用户可以输入目标、粘贴问题链接或一段报错，
通过 `/context add <path-or-reference>` 加入文件、截图或其他资料。
宿主提供的拖放与剪贴板附件可以映射为相同的资料操作。
选择项目后，系统结合已批准的项目资料生成工作草案。

首次使用项目时，用户确认仓库、可用执行能力、资料访问范围和资源额度。
资料发送到模型服务前，页面展示接收方及授权范围；
规划阶段的模型使用计入可见用量。
项目设置保存这些明确选择，供后续工作使用。
这是当前开发试点的配置基线，不是所有 OS 工作都必须先选择 Git 仓库的产品要求。
长期的工作上下文包括用户授权的目录、应用或执行环境；具体支持范围由适配器声明。

例如用户输入：

> 修复订单 CSV 导出漏行的问题，保持列格式不变。

系统形成一张可编辑的工作约定：

```text
修复订单 CSV 导出漏行
项目：订单服务

交付
修复改动、根因说明、回归验证记录

完成条件
1. 给定 1001 条订单，导出完整且无重复
2. 列名、顺序和字段表示保持一致
3. 覆盖空数据、单条数据和跨页边界

推进方式
调查与回归设计并行 → 修复 → 集成验证 → 交付

授权范围
在隔离现场读取代码、修改本工作文件并运行本地验证
修改接口约定、扩大资料访问、增加额度、对外发布时请求确认

资源
使用项目已批准额度；[查看并发、费用与运行时长约束]

[开始工作] [修改约定] [保存草案]
```

用户主要确认结果与边界。
Agent、分支、工作目录和执行任务是可展开的执行安排，
由系统在授权范围内选择并创建。
缺失信息按影响排序：决定目标含义的问题在开始前询问；
可由调查获得的信息进入执行计划。

### 4.2 不同大小的目标，共用同一条路径

“解释这段报错”直接得到回答，属于即时对话；
“导出修复为什么还没完成”属于已有工作的讨论；
“修好这个问题”形成持续委托，交付包含代码与验证。
用户在回答后说“那就修复它”，系统把相关说明与材料带入工作，
无需用户重新整理目标。明确委托的调查报告同样是一项工作。

工作约定的细节由系统起草、用户可编辑，执行的范围与风险在开始前可见；
即时回答不经历创建、开始和验收仪式。
“保存草案”保留意图；“开始工作”建立本次推进授权。

## 5. 授权后的自主推进

点击“开始工作”后，系统负责把工作推进到下一个需要人判断的边界：

```text
工作约定
   |
   +-- 调查问题 ------------+
   |                       |
   +-- 设计独立回归验证 ----+
                           |
                        实现修复
                           |
                        集成验证
                           |
                        准备交付
                           |
                        用户验收
```

计划依据依赖、输出与质量门槛组织执行。
一个任务的结果通过约定门槛后，系统把对应版本的结果交给后续任务。
验证失败时，根据失败证据和授权的重试额度安排修复。
局部失败对独立任务的影响由依赖关系决定。

### 5.1 协作以产物为中心

一项工作可以安排调查、实现、验证等不同能力并行参与。
每个写入任务拥有隔离的文件现场，结果进入统一的集成候选。
用户默认看到一份整合后的工作进展和交付。

工作站的“执行安排”可以展开查看：

| 任务 | 责任 | 输入 | 输出 | 状态 |
|---|---|---|---|---|
| 调查遗漏边界 | 调查执行者 | 目标、复现材料、代码基线 | 根因报告 | 已形成结果 |
| 编写独立用例 | 验证执行者 | 完成条件、数据约束 | 回归用例与期望 | 已通过门槛 |
| 实现修复 | 实现执行者 | 根因报告、固定版本用例 | 候选改动 | 正在执行 |
| 集成与检查 | 集成执行者 | 通过门槛的候选产物 | 交付候选 | 等待输入 |

系统安排能力时考虑任务要求、数据访问、可用资源和已批准策略。
用户可以指定执行者、固定某项安排，或让系统选择满足条件的能力。
默认不要求用户逐个启动开发与验收 Agent，或选择内部使用的 PowerShell/cmd。
执行者和 shell 的可调度范围限于已注册且获准的能力；已有现场的纳管需要明确
身份和所有权交接，不能把看见一个进程等同于可以操作它。

### 5.2 自动推进的边界

| 情况 | 产品动作 |
|---|---|
| 约定范围内的下一阶段已就绪 | 自动安排执行 |
| 可恢复失败且仍有重试额度 | 保存失败证据，自动重试并记录原因 |
| 修复会改变接口或交付定义 | 形成范围决定，等待用户授权 |
| 即将超过已批准的资源额度 | 停止新任务准入，展示增加额度或收缩工作的选项 |
| 缺少必需的资料或访问许可 | 展示所需资料、用途与授权动作 |
| 结果相互冲突或出现高影响风险 | 汇总证据和选项，形成决定 |
| 工作满足交付门槛 | 形成候选交付，进入用户验收 |

用户在工作约定中可以把特定阶段设为人工检查点。
系统遵循已确认的检查点，其余阶段按计划推进。

### 5.3 内部协作：派活，也负责收活与返工

系统向执行者交付明确任务：目标、输入、输出、完成条件和检查方式。
执行者确认接收，过程中报告发现与阻碍，最后递交带产物和证据的结果包。
“正在执行”“报告取得进展”“已递交结果”“检查通过”分别显示。

```text
任务派发 → 接收 → 执行与报告 → 递交结果 → 检查
                                      ├─ 通过 → 交给下游
                                      └─ 需要修改 → 新执行 → 新结果 → 再检查
```

例如修复执行者递交 R-7，检查发现 1001 条输入只导出了 1000 条。
系统把失败条件、检查记录、修改要求和应保留的格式处理交给修订执行，
得到 R-8 后再次检查。用户看到“跨页检查未通过，系统正在安排修订”，
无需复制错误信息、切换 Agent 或催促下一步。

缺少证据时先补证据；结果不符合约定时针对性修改；理解错误时重新澄清。
需要改变目标或增加投入时，系统才带着具体选择找用户。
内部检查、合并后检查和用户最终接受是三个不同环节。

执行者需要已有资料时，由系统在内部回答或安排定向交流。
新发现需要进一步调查时，系统调整任务安排并记录理由。
信息交接使用明确的材料与版本，而不是要求下游阅读一整段聊天自行猜测。

`/task show` 展示任务合同、当前执行、问题和结果；
`/result show` 展示递交内容、检查依据、打回理由和后续版本。
这些是可观察的执行细节，不是需要用户逐一管理的清单。

## 6. Console 内的工作站：深入现场，掌握整件事

默认入口是任务列表，打开任务先显示状态与该任务的对话。下面是用户主动展开
某项工作详情时的深层视图，不是查看或继续任务前必须经过的页面：

```text
Agent Console · 工作详情 · 订单服务
修复订单 CSV 导出漏行

目标：完整导出订单，保持列格式
状态：实现修复                         [暂停推进] [调整目标]

计划       现场       交付       决定       时间线

当前进展
遗漏定位于跨页结束条件
回归设计已覆盖 0、1、1000、1001 条数据
接下来：候选改动 → 集成验证

工作对话 / 文件 / diff / 报告 / 执行输出
这里展示所选内容；可切换或在 TUI 内分栏

shell 区域：隐藏
当前任务 > [继续讨论这项任务...]
```

工作站是这项工作在唯一 Console 内的聚合视图。对话、文件与证据都显示所属工作和版本。
查看某个执行时，还显示该执行的输入和产物范围。
关闭详情返回该任务的对话；`/work use <id>` 是可选的精确任务选择入口，
恢复该任务的对话与草稿，而不是只改变全局聊天的提示。
对话流、计划和结构化问题由工作模型驱动，TUI 负责键盘操作与呈现。

### 6.1 Shell 按需出现

```text
/shell list
/shell open
```

`/shell list` 展示调用者可访问的会话、所属工作、执行位置和显示状态，
可使用 `--work <id>` 筛选。`/shell open` 为当前工作准备合格的人工现场并打开会话；
工作正在写入的资源需要先进行写入交接，或选择独立的人工现场。
在全局上下文中打开 shell 时，用户明确选择工作，或通过 `--cwd` 建立标记为
“未关联工作”的人工会话。

打开 shell 后进入 Agent + Shell 布局。Agent Console 的工作上下文保持可见。
`/shell show <id>` 展示已有会话；没有会话时提供创建选择。
`/shell open` 和 `/shell show` 默认保留 Console 输入焦点；
`/shell focus <id>` 才进入该 shell 的交互输入。
`/shell hide` 隐藏本窗口的 shell 区域，并把焦点交回 Agent Console。
隐藏不会发送退出、取消或暂停指令。

实际 shell Tab 是会话的呈现位置。一项工作可以使用多个 shell，
很多后台任务也可以直接执行而不创建任何可见 shell。
多个窗口可以查看同一工作；同一交互 shell 的输入权通过明确的焦点/接管操作交接。
人工现场的写入权通过 `/workspace handback` 交回；隐藏 shell 时这项责任仍保留。
交付验收和冲突任务推进以写入责任已妥善交接为前提。
查看已有输出、diff 或报告不等于申请接管编辑。进入交互 shell 前，
界面明确展示它属于哪项工作、哪份代码，以及是否需要人工接管。

### 6.2 用户如何介入

| 用户意图 | 直接操作 | 系统处理 |
|---|---|---|
| 想知道原因 | 在协作区提问 | 使用当前工作事实回答，附相关证据 |
| 提供遗漏的例子 | 添加资料或补充说明 | 保存来源，判断影响，并交给相关执行 |
| 改变交付要求 | “调整目标”或表达变更意图 | 展示约定变化、受影响产物与新增投入，等待确认 |
| 亲自修改代码 | “接管编辑” | 完成写入交接，分配人工现场与写入权 |
| 控制执行节奏 | “暂停推进” | 停止新任务准入，并展示当前执行的收束进度 |
| 让系统接着推进 | “恢复推进”或“交回执行” | 验证现场，形成新输入版本，安排受影响任务 |

用户表达“我来改”或使用接管命令后，可在对应编辑器或终端直接工作。
表达“我改好了”或使用交回命令后，系统展示识别到的改动和后续安排，
将人工贡献记录为新的候选输入，重新验证的范围明确展示。
独立且不受改动影响的任务可以继续推进。
交回不要求依次隐藏、关闭所有 shell；已交回的现场可以保留为查看用途。
仍会写入的前台程序有明确的处理提示，不能用“已交回”的文字掩盖剩余动作。

“暂停推进”显示实际状态：等待安全检查点、正在取消可取消任务，或仍需处理的执行。
“已暂停”表示管理范围内的执行已经收束到确认的静止状态。
服务和执行位置的异常则使用“连接中断”“状态待确认”等具体说明。

### 6.3 中途带入资料与现场

用户可将已有目录、分支、报告或会话作为工作资料加入。
系统展示识别出的目标、文件状态、访问范围及可复用结论，
用户确认后建立对应引用或现场关联。
可写现场的管理从明确的写入交接开始，历史结果保留其实际来源。

## 7. 待办：让每次判断都能推动工作

### 7.1 问题卡

```text
修复订单 CSV 导出漏行
需要决定：这次修复覆盖到哪里？

已知事实
当前导出循环与分页接口都存在边界假设
本次约定要求修复导出完整性并保持输出格式

A. 修复导出循环（建议）
   保持接口约定；使用本次额度完成

B. 同时调整分页接口
   扩大改动范围；需要新增接口兼容性验证与额度

选择 B 时将展示工作约定的修改内容。

[选择 A] [选择 B] [查看证据] [稍后处理]
```

问题卡包括当前事实、待决定事项、建议、备选方案和影响。
建议明确标注来源。用户可以补充自己的方案，系统按同样的规则检查范围变化。

提交后先显示“决定已保存”，再展示“已应用到执行”或具体的送达处理状态。
范围变化被写入新的工作约定，相关计划、产物与授权同时更新。
无关任务继续按有效授权推进。

### 7.2 注意力排序

待办按影响、紧急程度、阻塞范围和用户设定的优先级排序。
同一原因的重复事件合并为一个可处理事项。
相关问题可以作为一个决定包展示，但每个具体义务保留自己的结果。

用户可以设定专注时段与提醒渠道。
界面内保留完整问题；桌面通知默认使用通用事件描述，打开后进入具体工作。
稍后提醒保留义务，在约定时间重新出现。

### 7.3 通知如何到达，如何不打断当前工作

执行者通过工作工具主动报告发现、阻碍和结果；运行时独立报告执行事实；
工作服务更新状态后向 Console 推送事件。正常协作不靠反复询问 Agent
“完成了吗”，也不要求用户刷新页面。

用户与 B 工作讨论时，A 需要决定，C 有交付：

| 发生的事情 | 当前界面的变化 |
|---|---|
| A 的普通进展 | 更新工作卡与时间线，保持 B 的输入目标 |
| A 的内部检查失败 | 展示系统正在修订，不自动要求用户处理 |
| A 出现用户必须做的取舍 | 新增带工作名称和原因的待办提示，不抢焦点 |
| 用户打开 A 的待办 | 在问题上下文中处理；返回 B 时恢复 B 的草稿和聊天阅读位置 |
| C 有最终交付 | 新增交付待办，用户自行选择查看时机 |

后台事件不切换当前工作、不改写输入对象，也不让每次工具调用都变成通知。
系统自己能回答的执行问题留在内部。仅当需要人的目标判断、取舍或最终接受时，
才把责任交给用户。

协调 Agent 由服务中的程序化驱动器唤醒：有关事件进入工作队列，
空闲时发起下一轮协调，忙时合并排队。普通文字流只更新界面；
已约定的下一任务由调度器直接推进。用户看到的是连续工作，不是一个等待催促的聊天回合。

### 7.4 实现也必须把责任交接完成

原型不能只展示“已通知执行者”“已安排修改”等文字。每次交接必须有协议回执
和下一责任方：接收任务、递交结果、检查结论、返工安排、续接确认或明确的等待事项。
执行者的“完成了”不能替代结果递交；协调者写了一段计划也不能替代实际任务操作。

用户回答早于执行者结束当前回合时，系统排队并确认续接，不丢失回答；
被询问的执行已经结束时，由系统从记录或新的澄清任务接住问题。
缺少检查证据就补检查，缺少任务结果就明确处理，不把它们停留成无主的状态。
这些是工作模式的实现规则，不是要求本轮先做生产级故障验证。

## 8. 交付：明确收到什么、为什么值得接受

```text
修复订单 CSV 导出漏行
候选交付 #2

结果
跨页数据完整导出，列格式保持一致

完成条件                         证据
1001 条订单完整且无重复           数据集结果与校验记录
列名、顺序、字段表示一致          格式对比
覆盖空数据、单条与跨页边界         回归用例记录

[查看改动] [运行记录] [根因说明]

已知限制：列出适用范围与尚未覆盖的情形
交付位置：显示实际目录、分支与固定提交
运行方式：显示适用于该版本的命令和前提

[接受交付] [提出修改] [查看现场]
```

候选交付是一个固定版本的结果包，包含产物、完成条件、证据与已知限制。
证据显示来源、适用版本和可检查内容。
用户检查的是候选交付的实际内容；修改后的产物会形成新的候选版本。

体验原型的代码交付默认是一份受管工作目录中的交付分支和固定提交。
卡片给出实际路径、版本、查看改动与运行入口；接受后保留该版本，
不会自动切换或合并用户原来的工作目录。需要合并或创建 Pull Request 时，
用户选择明确的交付动作。报告交付给出可打开的正文或文件，而不是“报告已完成”的回复。
这一基线使用户能实际检查和使用结果；其他交付方式仍由工作约定指定。

后续 OS 状态型工作还必须交付：目标资源与执行位置、改变前后的可观察状态、
对应操作与授权、验证时间和有效条件、未解决或未知副作用，以及可用的恢复方式
或不可逆限制。例如“服务已恢复”要有目标实例的健康观测，而不只是写出恢复报告；
“文件整理完成”要有清单与内容保留依据，而不只是成功退出的命令。
验收前状态失效、目标被替换或证据不足时，不能沿用旧证明接受。
这些是后续契约要求，当前 `LocalCode` / `Report` 协议没有因此获得新的结果类型。

### 8.1 接受、修改与发布

“接受交付”记录用户对该版本结果的认可。
如果工作约定要求对外交付，随后进入明确的交付动作和回执确认。
本地结果、代码提交、Pull Request、报告文件都可以成为约定的交付位置。

例如“接受并创建 Pull Request”展示目标仓库、分支、基线、
提交内容、标题、正文和访问范围。用户确认后，系统执行并记录外部回执。
首页根据工作约定所要求的交付条件显示“交付中”或“已完成”。

“提出修改”让用户对某个完成条件或证据给出反馈。
系统展示将修订的范围和资源影响。用户选择“按此修改并继续”后，
工作在有效授权内进入修订；扩大范围的修改先更新工作约定。

### 8.2 让结果产生后续价值

接受交付后，用户可以：

- 把结果提供给另一项已建立依赖的工作；
- 从结论创建后续工作，并带入选定的证据；
- 将经过确认的项目知识纳入项目资料；
- 归档工作，并管理执行资源的保留与清理。

下游使用明确版本的交付。上游结果更新时，
用户能够看到哪些后续工作需要重新评估，系统按约定策略处理影响。

## 9. 长时间推进、恢复与结束

### 9.1 离开与回来

工作由持续运行的工作服务管理。关闭一个窗口后，工作按执行位置的实际状态推进。
首页展示本机执行位置及其可用性；本机保持运行时，授权内任务可在后台进行。
设备休眠或关机后，持久工作记录、决定和交付保留，重新上线时进行恢复。

回来后首先展示：

```text
离开期间
1 项交付准备好
1 项决定等待你
2 项工作仍在推进

需要处理
订单导出：候选交付 #2
接口调整：选择兼容性策略
```

系统区分已确认的当前状态与待重新确认的执行。
可重连的执行接回同一项工作；需要新尝试时，
系统依据保存的工作约定、决定、产物和安全检查安排恢复。
存在未知副作用时，恢复页展示已知事实和需要确认的步骤。
执行者更换或上下文窗口耗尽时，产品负责在支持的适配器边界内重建获准的上下文、
核实续接状态并保留工作身份。不能把“你先 compact、重新启动 Agent，再重述目标”
作为普通工作流程；不支持自动续接时应显式阻塞，不能假装已经恢复。

### 9.2 资源与预算

每项工作显示已使用的资源、当前执行和已批准的剩余额度。
额度可以约束并发、自动重试、运行时间和可计量费用。
只有执行能力能够强制实现的约束才显示为硬限制；
估算值和提醒阈值采用不同标签。

用户可以批准增加额度、降低并发、缩小范围或暂停推进。
所有选择都展示对交付目标的影响。

### 9.3 完成工作的生命周期

| 动作 | 结果 |
|---|---|
| 隐藏 shell | 本窗口切回 Agent Focus；会话和工作执行保留 |
| 关闭指定 shell | 检查该会话及前台程序的影响，确认后关闭，工作记录保留 |
| 暂停推进 | 保留目标，等待执行收束后暂停 |
| 恢复推进 | 检查条件与授权，重新安排就绪任务 |
| 取消工作 | 收束执行，将目标记录为取消，保留已形成的结果 |
| 接受交付 | 记录认可；满足约定的全部交付条件后完成 |
| 重新打开 | 建立新的目标版本，并保留此前的验收记录 |
| 归档 | 将已结束工作纳入历史 |
| 清理执行资源 | 展示可清理资源、保留证据和数据风险，按确认执行 |

清理面板列出具体目录、分支和执行数据及其所有权。
未确认写入、未保存内容和未交付结果会形成需要处理的条件。
用户明确选择要保留的证据、数据和可删除资源，操作结果记录在工作历史中。

## 10. 核心用户故事：围绕工作，而不是工具

> 作为使用操作系统完成工作的用户，我希望只通过 Terminal 表达目标、讨论方案、
> 委托并行工作、查看进度和验收结果；系统负责选择获准的能力、管理现场和上下文、
> 安排执行与返工，不要求我管理命令、Agent 或 shell 会话。

以下是目标故事，不是已实现功能清单。US-01–US-12 保留原有身份以保持历史映射；
US-13、US-14 补充资源抽象和 OS 结果。自然语言主路径与键盘确认必须可用，
领域动作也提供同权限的结构化接口。后续适配器能力不得借当前试点的结果签收。

| ID | 用户意图 | 用户动作 | 产品结果 | 验收条件 |
|---|---|---|---|---|
| US-01 | 从对话自然进入委托 | “这是什么问题？”再说“帮我处理好” | 即时问答直接返回；持续委托沿用材料，确认约定后推进 | 零用户 shell 起步；不必启动 Agent、重复目标或为每次问答立项 |
| US-02 | 了解所有工作的状态与注意力 | “我的这些工作怎么样了，哪个需要我？”或查看首页 | 按工作显示目标、位置、真实进度、阻塞、交付与下一责任方 | 五项工作状态有来源与时间；未知明确标记，不能只汇总模型叙述 |
| US-03 | 让系统组织执行与返工 | 确认目标和推进范围 | 派发、内部问答、递交、检查、修订与下游交接连续发生 | 至少一次真实打回和再次通过，无需用户搬运信息或安排下一步 |
| US-04 | 从一个入口对话并管理所有现场 | “它在哪里做，为什么这么做？让我看看”；执行中继续讨论或查看另一工作 | 从同一入口解释实际计划、查看正确现场，后台工作继续 | 问答有计划与证据依据，不暂停执行或暗改目标；工作与 shell 选择分别明确 |
| US-05 | 亲自参与解决问题 | 补充资料，或申请接管编辑 | 更新上下文或完成安全写入交接 | 人工改动有来源，受影响验证重新安排 |
| US-06 | 跨工作做重要取舍 | 从当前工作进入另一项工作的待办，查看证据并选择 | 应用决定后返回原来的上下文 | 提示不抢输入目标；已保存、已应用和待确认状态可区分 |
| US-07 | 理解并改变工作方向 | “为什么用这个方案？不行，换一个”；确认目标与影响 | 提出有理由的替代方案，确认后实际修订计划；改变约定时形成新版本 | 保留兼容结果；旧候选与未派发指令按影响失效；已派发副作用先收束，不止回复“好的” |
| US-08 | 获得可信结果 | “完成了吗？我来验收” | 展示目标与实际结果、可检查证据和限制，保存验收回执 | 当前试点接受固定代码/报告版本；OS 状态型结果须另经 US-14 验证，聊天宣称不算完成 |
| US-09 | 推进结果修改或同时处理新问题 | “这里再改一下；另一个问题也同时看一下” | 明确修订与新工作目标，分别安排并保留版本关系 | 范围、输入、资源和责任明确；不把新问题混入旧工作的授权 |
| US-10 | 在失败或离开后继续获得进展 | 回来问“继续之前的工作”，处理必要确认 | 重连或安全安排新尝试，呈现原目标、有效决定与下一步 | 工作身份保留，未知副作用可见；适配器续接资格单独验证，不能假装上下文仍在 |
| US-11 | 用键盘控制工作与空间 | 自然语言或 slash commands 调整优先级、额度、暂停和恢复；按需查看现场 | 执行与呈现分别遵循同权限的领域动作 | 不强制手写命令或内部 ID；shell 隐藏、会话关闭、工作暂停有明确区别 |
| US-12 | 让完成的工作形成长期价值 | 发布、复用结论、归档或清理 | 保留交付与知识，管理剩余资源 | 来源、授权、保留内容与删除范围可检查 |
| US-13 | 不再管理内部工具和会话 | “你帮我完成”，只在必要时指定环境或执行偏好 | 系统选择获准能力、安排执行位置、管理 Agent/shell 和获准上下文 | 当前试点不依赖人工选择内部 shell/Provider 或启动下一执行者；已有资源纳管与更换后续接另行验证 |
| US-14 | 让操作系统里的实际目标达成 | “准备好这个环境”“恢复这个应用”“整理这些文件”并确认范围 | 受支持适配器执行并交付可观测的目标状态、操作来源和恢复限制 | 后续能力：状态、目标身份与时效匹配才可验收；不能把报告、进程退出或未经批准的副作用当作完成 |

## 11. 验证工作模式的连续场景

### 11.1 当前试点：一个入口完成两项真实工作

使用一个真实代码项目和两项真实工作，作为通用 task-driven Terminal 的首个场景。
项目与执行能力预先配置并授权；配置不要求用户在每个工作中重新选择 shell 或 Agent。
场景中的发现、结果和检查来自实际执行，而不是预设进度或假问题卡。
以下“分页/过滤”和边界缺陷是示例；重复实验可使用真实存在该行为的固定任务材料。
J1–J8 沿用验证计划中的身份；J9 是新增的对话与方案控制验收，历史轮次没有执行
J9 时不得补记为通过。表格是场景顺序示例，不要求各阶段只发生一次。

| Gate | 阶段 | 用户输入或动作 | 系统回应与界面变化 | 此时谁负责推进 |
|---|---|---|---|---|
| J1 | 即时问答 | 在全屏 Console 问“这段导出报错是什么意思” | 就地解释并引用材料，不创建待验收工作 | 系统回答，用户决定是否委托 |
| J1 | 转为工作 A | “修好它，保持列格式和接口不变” | 带入已有材料，展示精简工作约定，确认后开始 | 系统组织执行 |
| J2 | 建立工作 B | “另外调查构建为什么变慢”；随后讨论 B | 分别确认目标，A 保持推进，输入明确属于 B；不用另开 Agent | 系统保持两项工作的连续性 |
| J9 | 全局进度与方案讨论 | “这两件事到哪了？A 在哪里做，为什么用这个方案？” | 引用各工作实际状态、执行位置、计划和依据；普通问答不改目标、不停工 | 系统继续推进并说明事实 |
| J9 | 更换方案 | “A 换一个方案，B 继续” | 解释替代方案及影响，确认后变更 A 的实际计划和受影响执行；B 不被重定向 | 用户决定方向，系统落实 |
| J3 | 出现新发现 | 用户留在 B | A 的调查发现问题在过滤条件而非原先猜测；系统调整安排，将发现交给实现和检查执行 | 系统承担重新安排与信息交接 |
| J4 | 内部澄清 | 无用户动作 | 执行者询问列顺序约定；协调者从已确认资料回答，不创建用户待办 | 系统解决执行信息问题 |
| J5 | 内部打回 | 无用户动作 | 某次提交的边界检查实际失败；失败证据进入修订安排，新提交重新检查并通过 | 系统收活、检查、返工 |
| J6 | 重要取舍 | 在 B 的任务对话中出现 A 的问题，用户决定 | 问题解释两种范围的影响；回答后保留 B 的草稿，不要求用户转述给执行者 | 用户做取舍，系统应用 |
| J7 | 查看与贡献 | 回到 A 查看 diff；需要时说“我来改” | 显示准确的代码位置与现场，区分查看和接管 | 用户处理选定部分 |
| J7 | 交回工作 | “改好了，接着验证” | 展示人工改动摘要，安排受影响检查；shell 可以保留查看 | 系统接回后续工作 |
| J8 | 交付与修订 | 对候选提出“说明里补充边界原因” | 保留有效代码与证据，修订相关产物，返回新候选 | 系统组织局部修订 |
| J8 | 实际收到结果 | “完成了吗？我来验收”；查看目录、版本和报告 | 保留明确代码版本，报告可直接打开，工作结束而非仅聊天停止 | 用户判断结果是否解决目标 |

实验必须记录一次真实内部交接和一次真实不合格结果的修订闭环。
J5 必须由真实必需检查失败触发，用户提出报告修改的 J8 不能替代它。
允许为探索体验提供人工辅助，但须记录发生位置与内容，不能把人工规划、
转贴日志或催促执行当作系统自主完成。多 Agent 的数量不是成功指标。

无图形入口可用同一场景的一个变体验证：结构化客户端发起工作，
Console 处理实际需要人的决定，客户端取得同一工作的结果。
这不是另建一套 CLI 工作流程，也不要求本轮完成所有平台与宿主适配。
结构化变体可以证明领域能力，但不能替代对话主路径、原生输入和跨工作注意力的验收。

### 11.2 后续场景：OS 状态结果与资源连续性

在适配器和结果契约实现并声明支持后，使用隔离的测试应用和目录执行：

| 场景 | 用户语言 | 必需结果与反例 |
|---|---|---|
| OS-A：恢复测试应用 | “让这个测试服务恢复可用，保留原配置；顺便调查日志异常” | 系统定位获准实例并区分恢复与调查工作；真实健康检查、配置保留和副作用记录匹配。其他实例、权限不足或不可辨识状态不能被默认替代或报告为成功 |
| OS-B：整理测试文件 | “按这个规则整理这些文件，不丢原始内容” | 操作前后清单、内容摘要和目标位置可检查；重试不重复移动或覆盖。未授权目录保持不变，恢复能力与不可逆限制提前披露 |
| OS-C：接回受管现场 | “继续刚才的工作” | 已授权资源纳管或执行者更换后，原 Work、决定和证据保留；旧执行收束，新执行确认上下文后继续。不允许盲目接管普通进程或要求用户搬运会话上下文后声称自主续接 |

这些场景对应 US-13/14 和领域 AC-96–AC-98，是后续资格门槛，不是当前 v1
已支持的命令或产物类别。没有适配器时标记“计划中／未实现”；未来已承诺支持
但实际失败时必须记录 FAIL，不能用“超出试点”无限期豁免。

## 12. 产品质量标准

### 12.1 当前实验：责任是否真正转移

**北极星指标：工作级无人工编排的可信完成率。**

```text
分子 = 观察窗口内达到约定结果、证据有效、用户明确验收且完成，
       并且全程不依赖人工内部编排的唯一 Work 数
分母 = 本轮预先声明的支持范围内，进入批准执行阶段的全部唯一 Work 数
指标 = 分子 / 分母；分母为 0 时为 N/A，不能记为 100%
```

运行前固定任务集、支持的适配器与环境、源代码/运行二进制版本、授权额度、
观察窗口及所需旅程门槛。分母不能在看到结果后缩小：失败、阻塞、到期未完成、
批准执行后取消的工作仍计入，并分别列出原因；候选版本、重试和重新规划不增加
工作数。不同构建的结果分开报告，历史通过不自动转移到新版本或新要求。

同时报告**意图到工作启动的漏斗**：明确委托数、正确形成草案数、获批数、
实际启动数及各阶段失败/退出原因。问答不计作委托；外部前置不可用且尚未批准
的尝试单列。如果模型初始化失败而创建了零项工作，漏斗必须呈现失败，
不能因为北极星指标没有分母而隐藏入口不可用。

“人工内部编排”包括催促下一步、安排内部执行者、复制诊断或验收报告、
重复已有目标、手动选择内部 shell/启动 Provider、手工 compact/重建会话，
以及替产品核对内部交接的代码、部署版本与验收对象。首次环境/权限配置、
必要目标澄清、真正的业务或风险判断、最终验收和用户主动检查/贡献单列，
不误算成缺陷。测试操作者为证明运行版本而做的取证与设置也单列；
只有产品本身依赖用户完成这些动作才能推进时，才计为人工编排。

一个经人工接力后完成的 Work 可以记“已交付”，但不进入无人工编排的分子。
一个无人工介入却未完成的 Work 也不进入分子。自主执行不等于无人授权或无人验收。

| 观察项 | 工作模式成立的证据 |
|---|---|
| 下一步由谁安排 | 约定内交接与返工无需用户反复说“继续”“现在去验证” |
| 信息由谁搬运 | 日志、发现、产物和修改要求在内部递交；无需用户复制给另一个 Agent |
| 目标是否连续 | 问答转委托、工作切换、人工介入和修订后，无需重述已有目标 |
| 系统为什么找人 | 每次必需打断都对应人类判断，执行细节先在内部解决 |
| 修改后谁接手 | 系统识别人工贡献并组织后续工作，不让用户重排任务 |
| 工具由谁管理 | 正常推进不要求用户启动内部 Agent、选择 shell、压缩上下文或匹配交接版本 |
| 进度与方案是否可信 | 汇总回答对应当前工作事实；方案解释有计划和证据；确认变更后执行确实改变 |
| 结果是否到手 | 当前试点代码有目录、版本和运行入口，报告可读；OS 结果另需受支持适配器的目标状态证明 |

辅助指标记录每 Work 的人工编排次数、主动操作耗时、必要决定次数、
端到端完成时长、成本/额度与未知用量，以及最终结果是否正确。与手动多 Agent
方式比较时使用相同任务与环境，报告测量值而不是推测节省比例；速度不能抵消
错误交付、越权或未知副作用。“easiest”目前是产品承诺，不是已经得到的比较结论。

**当前里程碑签收：** 同一明确构建上的连续场景 J1–J9 全部达到要求，
包括真实检查失败后的自动返工；两项工作均有实际交付与明确验收，
所需内部交接的人工编排次数为零，且无未解决的结果完整性或授权问题。
单次 100% 不能证明所有旅程门槛，也不能推广为任意 OS 任务成功率。
每项功能须分别链接 US、AC、测试用例、运行证据与状态；
PASS、FAIL、BLOCKED、NOT RUN 的口径见[验证计划](agent-center-verification-plan.md)。
组件、原生交互、真实模型旅程和发布覆盖分别记录，不能互相顶替。

### 12.2 完整产品的后续质量目标

下列数值和工程属性是完整产品的目标，不作为当前工作模式实验的前置验收。
评估使用固定任务数据和明确设备条件，分别测量操作时间、等待时间、
判断正确率和交付质量。

| 维度 | 目标门槛 |
|---|---|
| 工作直接入口 | 新窗口创建一个 Console 和零个用户 shell，完整工作流程可在 shell 隐藏状态完成 |
| 意图到开始 | 已完成项目配置的用户，60 秒内从一句目标完成工作约定确认 |
| 注意力定位 | 面对五项工作，30 秒内准确指出全部需要本人判断的事项与原因 |
| 现场可达 | 一次命令选择工作或展示已有 shell，目标上下文保持可见且不重复创建会话 |
| 自主推进 | 一项包含并行调查、实现、验证的授权工作，在计划内自动完成全部内部交接 |
| 判断有效性 | 每条阻断式待办都具有具体问题、依据、行动与预期影响 |
| 决策可信 | 保存成功与应用成功分别可识别；失联、重复提交和过期决定有确定结果 |
| 结果可信 | 每个必需完成条件都有可检查且版本匹配的依据 |
| 人工控制 | 接管、暂停、取消后的实际写入状态准确展示 |
| 恢复连续性 | 重新进入后，60 秒内找到原目标、有效决定、当前交付和下一步 |
| 操作成本 | 创建与管理所需输入随工作复杂度展开；常规工作使用项目已批准默认值 |
| 键盘覆盖 | 主要工作故事可自然语言表达并用键盘确认；确定性 slash command 提供等价控制，不作为必学前提 |
| 可访问性 | 所有主流程支持键盘、可读状态和窄终端布局；附件核心流程支持路径/引用输入 |
| 无图形宿主 | 普通 TTY 使用相同 TUI，非交互 CLI/MCP 可读取和操作授权内工作并取得结构化结果 |
| 资源透明 | 已用、预估、硬限制、提醒阈值与未知值分别标识 |

## 13. 关键设计取舍

| 选择 | 对用户价值的贡献 | 产品承担的成本 |
|---|---|---|
| 每窗口唯一 Agent Console | 一个入口管理全局工作，直接进入 Agent Focus | 独立 XAML 宿主、TUI 生命周期与多窗口上下文 |
| 工作身份高于工具与会话 | 用户围绕目标和结果组织工作，不负责内部 Agent 或上下文生命周期 | 能力选择、环境身份、输入交接与适配器资格 |
| Terminal 提供按需运行资源 | 工作可以使用零到多个 shell，执行与显示分别控制 | 会话、物理呈现、输入权与工作身份分离 |
